AI Primer

Personal study reference — terminology grouped by topic
AI Workflow
Phase 0 — Build the model (done once by the AI lab)
Data Collection
Gather a massive text corpus — books, web pages, code, scientific papers, Wikipedia. Trillions of tokens. The breadth and quality of this data sets the ceiling on everything the model can ever know or do.
Data Curation
Deduplicate, filter low-quality text, remove PII, balance domains. A model trained on uncurated web data inherits its biases and noise. Curation is where most of the quality work happens before a single weight is updated.
Pre-training
The main training run. The model is shown text and learns to predict the next token — billions of times, across the full corpus. Runs on thousands of GPUs for weeks or months. Produces a base model that can predict text but has no helpful behaviour.
Forward Pass
The model processes a batch of tokens and outputs a prediction for what comes next. Each token attends to all previous tokens through the transformer layers, producing logits over the vocabulary.
Loss Calculation
Cross-entropy loss measures how wrong the prediction was. If the correct next token was "cat" and the model assigned it 10% probability, loss is high. If it assigned 90%, loss is low. Training minimises this number across every token in the corpus.
Backpropagation
After the forward pass computes loss, backprop calculates how much each weight contributed to that error — working backwards through every layer. Produces a gradient for each weight: "if I nudge this weight up, does loss go up or down?"
Gradient Descent
Each weight is nudged in the direction that reduces loss, scaled by the learning rate. Repeat forward pass → loss → backprop → weight update millions of times. The model slowly learns language structure from the statistical patterns in the data.
Learning Rate
How large each weight update is. Too high: training overshoots and becomes unstable. Too low: training converges too slowly. Typically starts higher and decays over time (learning rate schedule).
Batch Size
How many training examples are processed together before weights are updated. Larger batches give more stable gradients. Modern LLM training uses very large batches — millions of tokens per step — to utilise thousands of GPUs efficiently.
Epoch
One full pass through the training data. LLMs are often trained for less than one epoch — the dataset is so vast that seeing each document once is enough. Fine-tuning uses multiple epochs on smaller datasets.
Base Model
The output of pre-training. Excellent at predicting and completing text. Knows a vast amount about the world. But ask it a question and it may complete the question rather than answer it — it has no concept of being an assistant yet.
Instruction Tuning
Fine-tune the base model on instruction-response pairs: "Summarise this text" → [good summary]. The model learns to follow directions rather than just continue text. The step that turns a text predictor into a useful assistant.
RLHF
Reinforcement Learning from Human Feedback. Humans rank pairs of model responses. A reward model learns to predict human preference scores. The LLM is then trained with reinforcement learning to produce responses the reward model rates highly. Shapes the model toward helpful, harmless, and honest behaviour.
Reward Model
A separate model trained to score how good a response is. Takes a prompt + response as input, outputs a scalar score. Used during RLHF to give the policy model a training signal — the policy tries to maximise reward model scores.
RLAIF / Constitutional AI
Instead of human rankers, an AI model evaluates responses against a written set of principles (constitution). Anthropic's approach for Claude. Cheaper to scale than RLHF and produces more consistent, auditable alignment criteria.
RL Post-training
Reinforcement learning applied after instruction tuning to develop capabilities that supervised training alone doesn't produce reliably: multi-step reasoning, tool use, long-horizon planning. The training step behind modern "reasoning models."
Evaluation & Red-teaming
Benchmark the model on standard tests (MMLU, HumanEval, etc.) and deliberately probe for harmful outputs, jailbreaks, and failure modes before release. Red-teaming is a systematic adversarial process — not just QA.
Quantisation
Reducing weight precision from 32-bit or 16-bit floats to 8-bit or 4-bit integers. Makes the model smaller and faster with minimal quality loss. Required to run large models on consumer hardware or serve them cost-effectively at scale.
Deployment
The trained, quantised model is loaded onto inference servers and exposed via API. From here, every call you make runs against these frozen weights — the model itself doesn't change. Updates require a new training run. This is where Anthropic's job ends and yours begins.
Phase 1 — Prepare your knowledge (optional — only if using RAG)
⚠ RAG is optional
Phases 1 and 2 only apply if you are grounding the model in your own data — documents, databases, internal knowledge. If you are writing prompts directly and calling the model without external retrieval, skip to Phase 3.
Raw Data
Documents, PDFs, web pages, code, databases — anything the model should be able to reference. Raw data is unstructured and too large to fit in a prompt. It must be processed before the model can use it.
Chunking
Splitting raw documents into smaller pieces — typically 200–500 tokens with some overlap between chunks. Too large: the chunk contains unrelated content. Too small: it loses surrounding context. This is the step most RAG quality problems trace back to.
Embedding Model
A separate, smaller model that converts each chunk into a vector — a list of numbers representing its meaning. e.g. "sprint velocity" → [0.2, -0.8, 0.4, ...] Similar chunks produce similar vectors. This model runs once per chunk during preparation.
Vector
The numerical output of the embedding model — typically 768 to 1536 floating-point numbers per chunk. The actual numbers have no human-readable meaning; only the relationships between vectors matter.
Vectorizing
The act of running all chunks through the embedding model to produce their vectors. A one-time batch operation when new documents are added to the knowledge base.
Vector Store
A database that stores each chunk alongside its vector. Optimised for fast nearest-neighbour search. e.g. Pinecone, Weaviate, pgvector. This is what gets searched at query time.
Phase 2 — Handle a query (done per request, online)
User Query
The question or instruction from the user. Raw text. Before anything else happens, it must be converted into the same vector space as the knowledge base so relevant chunks can be found.
Query Embedding
The user's query is run through the same embedding model used on the documents. Produces a single query vector. This must be the same model — different embedding models produce incompatible vector spaces.
Vector Search
The query vector is compared against all stored chunk vectors using cosine similarity. Returns the top-k most similar chunks — the parts of the knowledge base most relevant to the query.
Cosine Similarity
Measures the angle between two vectors. Score of 1 = identical meaning. Score of 0 = unrelated. Score of -1 = opposite. Used to rank retrieved chunks by relevance.
Re-ranking
An optional second pass — a separate model re-scores the top-k chunks for true relevance before injection. More accurate than raw cosine similarity but adds latency.
Context Assembly
The retrieved chunks are combined with the system prompt and the user's query to form the full prompt. Order matters — most models attend better to content near the beginning and end.
Phase 3 — Build the prompt
System Prompt
Instructions placed before the conversation. Defines the model's role, behaviour, constraints, and any injected context (retrieved chunks, user data, wisdom). Not visible to the end user.
Retrieved Context
The relevant chunks from the vector search, inserted into the prompt. This is what makes RAG work — the model answers from what it was given, not from what it learned during training.
User Message
The human turn of the conversation. In agent pipelines this often includes injected data — not just what the user typed, but dynamic context added at call time.
Full Prompt
Everything the model sees: system prompt + retrieved context + conversation history + user message. Measured in tokens. The model has no memory beyond this — if it's not in the prompt, the model doesn't know it.
Tokenisation
The full prompt text is split into tokens — roughly 0.75 words each. The model never sees raw text, only token IDs. The context window limit (e.g. 200k tokens) caps the total prompt size.
Prompt Caching
If the system prompt is identical to a recent call, the provider reuses the cached KV pairs instead of reprocessing those tokens. Reduces cost and latency when the same system prompt is reused across many calls.
Phase 4 — Inference (inside the model)
Embedding Layer
Each input token ID is converted to a dense vector representation. This is the model's internal embedding — different from the RAG embedding model, and not directly accessible. First step inside the transformer.
Attention
At each layer, every token attends to every other token — assigning weights to decide which context is relevant to predicting what comes next. "The cat sat on the mat, it" — attention puts high weight on "cat" when processing "it".
KV Cache
The key-value pairs computed during attention are cached so they don't need recomputing for each new output token. Without KV cache, generating 500 tokens would require 500 full forward passes. With it, only new tokens need processing.
Forward Pass (inference)
Same operation as training — one complete run through all transformer layers — but no backpropagation follows. At inference time the weights are frozen; the forward pass only produces a prediction, it does not update anything.
Logits
The raw unnormalised scores the model outputs for every possible next token after the forward pass. A vector the size of the vocabulary (~100k entries). These scores are then converted to probabilities.
Phase 5 — Generate output (token by token)
Logits
The raw, unnormalized scores the model assigns to every token in its vocabulary at the end of the forward pass. One number per token — can be negative, zero, or large positive. Higher = model thinks that token more likely. Not probabilities yet. e.g. "mat": 4.2, "floor": 3.8, "banana": -2.3. Softmax converts these into probabilities.
Softmax
Converts the raw logits into a probability distribution — every possible next token gets a probability, and they all sum to 1. e.g. "the": 45%, "a": 30%, "one": 15%, "some": 8%, "every": 2%.
Temperature
Applied to logits before softmax. Low (0): always picks the highest-probability token — deterministic. High (1+): flattens the distribution, making unlikely tokens more probable — creative but unpredictable.
Top-p Sampling
Keep adding tokens in probability order until their cumulative probability reaches p. With p=0.9: "the" (45%) + "a" (30%) + "one" (15%) = 90% — stop there. "some" and "every" are cut. The number of candidates varies based on how concentrated the distribution is.
Top-k Sampling
Keep only the k highest-probability tokens. With k=3: only "the", "a", "one" survive. Simpler than top-p — fixed count regardless of probability distribution shape. Often used together with top-p.
Token Selected
One token is sampled from the filtered distribution. This token is appended to the output and also appended to the input for the next step — the model generates one token at a time, left to right.
Stop Token
A special token that signals the model is done. Generation halts when the model produces a stop token or hits the max_tokens limit. The response is everything generated before the stop token.
Phase 6 — Deliver the response
Detokenisation
The output token IDs are converted back to text. The reverse of tokenisation. Happens automatically — you never see the token IDs in the API response.
Streaming
Each token is sent to the client as it's generated rather than waiting for the full response. The user sees text appear word-by-word. Reduces perceived latency significantly for long responses.
Completion
The final assembled text returned by the API. What you see in the response object. Input tokens + output tokens = total tokens billed for the call.
Foundation
1 — The field
AI
The broad goal: machines that exhibit intelligent behaviour. Not a technique — a target. ML is the main method used to reach it.
Machine Learning (ML)
Algorithms that learn patterns from data instead of being explicitly programmed. You show the system examples; it figures out the rules. AI is the goal; ML is the method.
Deep Learning
A subset of ML using neural networks with many layers. "Deep" = many layers. Powers all modern LLMs, image recognition, and speech models.
Neural Network
Layers of interconnected nodes that transform input into output. Each connection has a weight. Think of it as a pipeline of math operations, where training adjusts every number until the output is useful.
2 — Types of AI
Narrow AI
AI that excels at one specific task — chess, image recognition, language — but cannot generalise beyond it. All current AI systems, including Claude, are narrow AI.
AGI
Artificial General Intelligence — hypothetical AI that matches or exceeds human reasoning across all domains. Does not yet exist. The stated long-term goal of Anthropic, OpenAI, and DeepMind.
Predictive AI
Takes input and outputs a category or number — classifying or forecasting based on patterns. e.g. a spam filter labels emails; a demand model forecasts sales. Existed long before generative AI.
Discriminative Model
A predictive model that learns the boundary between classes. Asks: "given this input, which bucket?" rather than "generate something new." Most traditional ML classifiers are discriminative.
Generative AI
Produces new content — text, images, code, audio — rather than classifying existing input. LLMs are generative. The output is something that didn't exist before.
Multimodal
A model that handles more than one input type: text, images, audio, video. Claude 3+ is multimodal — send it a screenshot and it reasons about both the image and your text question.
3 — The models
Model types
See the Models section for a full taxonomy — by input/output, reasoning capability, size, training approach, and specialization.
4 — What happens under the hood
Parameters / Weights
The numerical values inside a model — billions of numbers learned during training. Every connection in the neural network has a weight. More parameters = more capacity to represent complex patterns. GPT-4 has ~1 trillion.
Training
The process of adjusting a model's weights by showing it examples and minimising prediction error. A one-time (or infrequent) expensive process — not something that happens when you send a message.
Inference
Running a trained model to get a response. What happens every time you send a message. Fast and cheap relative to training — but with billions of users, still the dominant cost for AI companies.
Model
The trained artifact — a file of weights that maps inputs to outputs. "Calling the model" means running inference. The model itself doesn't change; only your prompt changes.
Models
1 — By input / output type
Foundation Model
A large model trained on broad data that serves as a starting point for many tasks. Not specialised for anything — adapted afterward via fine-tuning or RLHF. LLMs are one type of foundation model.
Large Language Model (LLM)
Text in, text out. Trained on massive text corpora to predict the next token. The most common model type. e.g. Claude, GPT-4, Gemini, Llama.
Vision Language Model (VLM)
Image + text in, text out. An image encoder converts pixels to embeddings that merge with token embeddings before the transformer processes them. e.g. GPT-4o, Claude 3+, Gemini. Enables: "describe this screenshot", "what's wrong in this diagram."
Audio Model
Speech or audio in, text or audio out. Covers speech-to-text (transcription), text-to-speech (synthesis), and voice agents. e.g. OpenAI Whisper (STT), ElevenLabs (TTS).
Multimodal Model
Accepts any combination of text, image, audio, and video. Output is typically text or generated media. The direction frontier models are all moving. e.g. GPT-4o, Gemini 2.0.
Diffusion Model
Generates images or video by learning to reverse a noise process. Not a transformer — a different architecture entirely. e.g. Stable Diffusion, DALL-E, Sora. Input: text prompt. Output: image or video.
Embedding Model
Text in, vector out — no generated text. Converts sentences into numerical representations for search, similarity comparison, and RAG retrieval. e.g. OpenAI text-embedding-3, Cohere Embed.
2 — By reasoning capability
Standard LLM
One forward pass per response. Fast, cheap. Commits to output tokens immediately without deliberation. Best for most tasks.
Large Reasoning Model (LRM)
Trained via reinforcement learning to generate thinking tokens before answering. Deliberates before committing to a response. Trades latency and cost for accuracy on hard problems. e.g. OpenAI o3, o4-mini, Claude with extended thinking, Gemini 2.5 Pro, DeepSeek-R1.
3 — By size / deployment
Frontier Model
The largest, most capable models — API-only, run in massive data centers. Highest quality, highest cost. e.g. GPT-4o, Claude Opus, Gemini Ultra.
Small Language Model (SLM)
Compact models (1B–7B parameters) designed to run on consumer hardware. Lower quality than frontier but fast, cheap, and private. e.g. Phi-3, Gemini Nano, Llama 3.2 1B/3B.
Edge Model
A model small enough to run on the device itself — phone, laptop, car — without sending data to a server. No internet required, no API fees, instant response, data stays private. Achieved via quantization, pruning, and distillation. e.g. Apple Intelligence on-device, Gemini Nano on Pixel.
4 — By training approach
Base / Pre-trained Model
Raw output of pre-training — next-token prediction only, no instruction following. Will complete your sentence, not answer your question. Starting point for all further training.
Instruction-tuned Model
Fine-tuned on (prompt → response) pairs so the model follows instructions and holds conversations rather than just completing text. Most deployed models are instruction-tuned.
RLHF Model
Further aligned via human feedback — humans rank outputs, a reward model learns those preferences, the LLM is trained to score higher. Produces the personality, tone, and safety behavior you see in Claude and ChatGPT.
5 — By role in the pipeline
Reward Model
Trained on human preference data to score how good a response is. The backbone of RLHF — the main LLM is trained to produce outputs the reward model scores highly. Never deployed to users; exists only to guide training.
Critic Model
Similar to a reward model but used during RL inference — evaluates the value of a state or action rather than scoring a finished output. Common in actor-critic RL setups where the critic guides the actor (main model) during training.
Draft Model
A small, fast model used in speculative decoding. It generates several candidate tokens cheaply; a larger model then verifies them in parallel. If accepted, you get the quality of the big model at the speed of the small one. Used to reduce latency in production.
Reranker Model
Scores the relevance of retrieved documents against a query. Used in RAG pipelines after initial vector search to improve result quality before passing context to the LLM.
6 — By learning objective
Generative Model
Learns the underlying distribution of data so it can produce new examples. Asks: "how would I generate this?" Output is new content — text, images, audio. e.g. GPT, Claude, Stable Diffusion, DALL-E. LLMs are generative models.
Discriminative Model
Learns to draw a boundary between classes. Asks: "which category does this belong to?" Output is a label or score, not new content. e.g. BERT, image classifiers, spam filters, sentiment analysis models. Rerankers are discriminative.
BERT vs GPT
BERT is discriminative — trained to predict masked tokens (fill in the blank), making it better at classification tasks. GPT is generative — trained to predict the next token, making it better at producing text. Both use the transformer architecture but with different objectives and different halves of it (encoder vs decoder).
8 — By architecture variant
Mixture of Experts (MoE)
Instead of activating all parameters for every token, the model routes each token to a subset of specialist sub-networks ("experts"). Same parameter count as a dense model but a fraction of the compute per token — faster and cheaper at scale. e.g. GPT-4, Mixtral, Gemini.
9 — By specialization
Code Model
Trained heavily on code — higher accuracy on programming tasks, code completion, debugging. e.g. GitHub Copilot, DeepSeek Coder, Code Llama.
Domain Model
Fine-tuned on a specific field — medicine, law, finance — to improve accuracy in that domain. Narrower but more reliable within its scope than a generalist model.
How LLMs Work
0 — The math layer
Why math?
Computers can't read images, text, or audio directly. Linear algebra is the translation layer — it converts raw data into numbers a machine can compute on. Everything an LLM does is built on top of this.
Scalar
A single number. The simplest unit. 5, 2.6, π. A pixel's brightness is a scalar. A temperature reading is a scalar.
Vector
A 1D list of numbers. [2, 3, 4]. A word or sentence encoded as meaning is a vector — called an embedding. Vectors represent position in high-dimensional space; similar meanings cluster nearby.
Matrix
A 2D grid of rows and columns. An image is a matrix where each cell is a pixel intensity. A dataset of users and movie ratings is a matrix. Most neural network operations are matrix operations.
Tensor
A generalization of vectors and matrices to 3+ dimensions. A video (frames × height × width × color channels) is a tensor. TensorFlow is named after them.
Matrix dot product
The single most important operation in linear algebra for ML. Used in every neural network from simple to transformer. It combines two matrices to produce a third — the core of how layers in a network transform data as it flows through.
0b — Measuring similarity
Why similarity matters
Once sentences are embeddings (vectors), you can measure how related they are mathematically. This powers search, RAG retrieval, and semantic comparison.
Euclidean distance
Point-by-point difference across all dimensions, squared, summed, square-rooted. Measures the straight-line distance between two vectors. Output is unbounded — bigger number means more different. Good when magnitude matters.
Cosine similarity
Measures the angle between two vectors, not the distance. Output: -1 to 1. Score of 1 = same direction (similar meaning). Score of 0 = perpendicular (completely independent features). Score of -1 = opposite direction. Standardized — preferred for text embeddings because magnitude doesn't skew the result.
0c — Dimensionality reduction
The problem
Training on billions of tokens with every dimension active is impractical. Most dimensions carry noise, not signal. Dimensionality reduction keeps the useful structure and discards the rest.
SVD (Singular Value Decomposition)
Breaks one large matrix A into three smaller matrices: U (row/user features) × Σ (importance rankings, largest first) × Vᵀ (column/item features). You then keep only the top-ranked features and discard the rest — the signal without the noise. Works on any matrix shape.
SVD example
A movie ratings matrix (users × movies) decomposes into a user-behavior matrix, an importance-ranking diagonal, and a movie-feature matrix. Reconstruct with only the top features: you now have a compressed representation that captures taste patterns without storing every rating.
1 — Text to numbers
Token
The atomic unit of text an LLM processes — roughly 0.75 words. "Hello Scrum" = 3 tokens. Everything is measured in tokens: cost, speed, limits.
Tokenisation
Splitting raw text into tokens before the model sees it. Different models use different tokenisers, so the same sentence has a different token count in GPT vs Claude.
Embedding
Each token is converted to a vector — a list of numbers representing its meaning. Similar words get similar vectors. This is how the model "understands" language mathematically.
Latent Space
The high-dimensional space where all embeddings live. Similar concepts cluster together. The model reasons by navigating this space.
2 — The architecture
Transformer
The neural network architecture behind all modern LLMs. Introduced 2017. Processes all tokens in parallel using self-attention — unlike older models that processed one token at a time.
Attention
The core mechanism inside a Transformer. At each generation step it asks: "which other tokens in the input are most relevant to predicting this next token?" and weights them accordingly.
Pre-training
The initial training run on massive text data (books, web, code). The model learns to predict the next token billions of times. Produces a base model with broad language understanding but no specific behaviour.
3 — A call to the model
Prompt
Everything sent to the model in one call — system message + conversation history + user message combined. The model only sees the prompt; it has no memory of previous calls.
System Prompt
The first part of the prompt. Sets the model's role, behaviour, and constraints before any user input. Not visible to the end user. Hello Scrum's 14 prompts all start here.
User Prompt
The human turn of the prompt. In agent pipelines this often includes injected context — file contents, data, dynamic instructions — not just what a human typed.
Multi-turn
A conversation with multiple exchanges. Each turn appends to the prompt, growing the context window. Hello Scrum's story elaboration uses a multi-turn tool-use loop.
Context Window
The maximum tokens the model can process in one call — input + output combined. Claude's window is 200k tokens. Exceeding it requires truncation or summarisation.
Completion
The model's generated response. Produced one token at a time, left to right, each token chosen based on all previous tokens in the prompt plus what has been generated so far.
Streaming
Tokens sent to the client as they're generated rather than waiting for the full response. Hello Scrum uses SSE streaming so the live log updates in real time.
4 — Controlling output
Temperature
Controls how randomly the model picks each next token. 0 = always picks the most likely token (deterministic). Higher = picks less likely tokens more often (creative / unpredictable).
Top-p (Nucleus Sampling)
At each step, restricts token selection to the smallest set whose cumulative probability reaches p. Cuts off the long tail of unlikely tokens. Works alongside temperature.
Top-k
Restricts token selection to the k most likely candidates at each step. A simpler alternative to top-p. Often used together with it.
Structured Output
Constraining the model to respond in a specific format — JSON, XML, a schema. All 14 Hello Scrum prompts use structured output. Without it, responses require brittle regex parsing.
5 — Advanced concepts
In-context Learning
Adapting model behaviour by placing examples in the prompt — no weight updates, no retraining. Few-shot prompting is in-context learning. The model generalises from examples it sees at call time.
Test-time Compute
Spending more compute at inference time rather than training time to improve quality. The second major scaling axis alongside model size. See section 7 for the full breakdown.
Vibe Coding
Accepting AI-generated code without detailed review. Fast but risky — bugs and scope creep go undetected. Hermes and test suites are the antidote in Hello Scrum.
6 — Failure modes
Hallucination
The model generates plausible-sounding but factually wrong content. Root cause: the model is predicting probable text, not retrieving verified facts. RAG and grounding reduce it.
Instruction Following Failures
The model ignores or partially follows explicit instructions — wrong format, skipped constraints, drifting to a different task. Gets worse with long prompts and conflicting instructions.
7 — Test-time compute
The two scaling axes
For years the only lever was train-time compute — bigger models, more data, more GPU time. Those weights then froze. Test-time compute is the second axis: spend more compute at inference time, on the problem that needs it, per query.
Train-time compute
CAPEX — paid once. Months of training, millions of dollars. Weights are frozen after. Every query, easy or hard, gets the same one forward pass. If the first token goes down the wrong path, the model just keeps going.
Test-time compute
OPEX — paid per query, adjustable per query. The model gets a budget and decides how to spend it. A 2024 Google DeepMind paper showed a 3B parameter model using test-time search beat a 70B model on hard math problems.
Thinking tokens
Tokens generated before the actual response — a scratchpad. In a standard forward pass the model commits to final-answer tokens from word one. Thinking tokens let it explore, backtrack, and try a different angle before committing to anything the user sees.
Reasoning models
Models trained via reinforcement learning to generate thinking tokens automatically. The RL process rewards intermediate reasoning steps, so the model learns to do chain-of-thought without being prompted. Claude's extended thinking and OpenAI's o-series are examples.
Three mechanisms
Can be combined. All three trade compute for accuracy — more flops per query, higher probability of a correct response.
Chain of thought
Model reasons step-by-step before answering. The scratchpad approach. Query → reasoning tokens → answer. Baked into reasoning models via RL; can also be prompted manually with "think step by step."
Tree search
Instead of one greedy forward pass, the model branches into multiple reasoning chains. A verifier scores each branch and picks the most promising one to continue. More expensive but better on complex problems.
Self-consistency
Run the same problem N times at high temperature, take a majority vote. No verifier needed — the statistical distribution of the model's own outputs is the signal. If 7 of 10 independent chains land on the same answer, confidence is high.
Trade-offs
More latency (45-second responses frustrate users). Thinking tokens billed as regular output tokens — expensive at scale. Overthinking degrades performance on simple questions — the model talks itself out of the right answer.
Adaptive routing
Best practice: route easy queries to fast single-pass inference, hard queries through the full reasoning pipeline. ChatGPT uses a picker to route between reasoning and non-reasoning models per query.
Prompt Engineering
1 — How many examples to give
Zero-shot
No examples — just instructions. "Classify this email as spam or not spam." Works for simple well-defined tasks. Fails when the model needs to match a specific output format it hasn't seen.
One-shot
One example before the task. Input: "I won a prize!" → Output: positive. Now classify: "My flight was cancelled." The single example shows the model the expected format.
Few-shot
2–5 examples before the task. Each additional example narrows down what "correct" looks like. Most reliable for structured output — the model learns format, tone, and edge cases from the examples.
2 — Reasoning strategies
Chain of Thought (CoT)
Ask the model to show its work step by step before answering. "Think through this step by step." For a maths problem: the model writes out intermediate steps rather than jumping to an answer. Accuracy on hard problems improves significantly.
Tree of Thoughts (ToT)
Extends CoT by exploring multiple reasoning branches in parallel before committing to one. Like asking the model to consider several approaches, evaluate each, then pick the best. More compute, better answers on complex problems.
ReAct
Reason + Act. The model thinks → calls a tool → observes the result → thinks again → repeats. Used in agents: the model doesn't just reason in its head, it takes actions and adjusts based on what it finds.
Reflexion
The agent critiques its own prior attempt before retrying. After a failed action, it writes a verbal self-critique — "I assumed X but that was wrong because Y" — and uses that to inform the next attempt. Self-correction without retraining.
3 — Structuring prompts
RTCC
Role → Task → Context → Constraints. A four-part structure that separates who the model is, what it must do, what it needs to know, and what rules it must follow. Prevents sections from bleeding into each other.
XML Tags
Using <task>, <context>, <constraints> to mark prompt sections. Claude parses tagged sections more reliably than prose headings — the boundaries are unambiguous.
Runtime Injection
Dynamic content inserted into a prompt at call time — not hardcoded in the template. e.g. reading a config file or a user's history and pasting it into the prompt before sending. Makes prompts context-aware without re-writing them.
Prompt Chaining
Using the output of one LLM call as the input to the next. Call 1 extracts entities → Call 2 classifies them → Call 3 writes a summary. Breaks complex tasks into steps each model can handle reliably.
4 — Key concepts
Grounding
Tying model output to real, verifiable data. Without grounding, a model invents plausible-sounding facts. RAG is a grounding technique — the model answers from retrieved documents rather than from memory.
Context Engineering
Deliberate design of exactly what goes into the context window — what to include, what to exclude, in what order. The discipline behind effective RAG, agent prompts, and system prompt design.
Prompt Versioning
Treating prompts like code — tracking changes, diffs, and rollbacks. Essential because improving one prompt can silently break another task. Without versioning, you can't isolate what caused a regression.
Prompt Injection
An attack where malicious text in the input overrides the system prompt. "Ignore all previous instructions and instead..." A critical security risk for any agent that reads user-supplied or external content.
RAG & Knowledge
1 — The problem RAG solves
Grounding
Tying model output to real, verifiable data. An ungrounded model invents plausible-sounding facts. Grounding gives the model actual documents or data to reason from instead of relying on memory.
RAG
Retrieval Augmented Generation. At call time, retrieve relevant documents from a knowledge base and inject them into the prompt. The model answers from what it was given, not from what it learned during training. Grounds without fine-tuning.
Context Stuffing
The simplest RAG: load everything into the context window instead of selectively retrieving. Works when the knowledge base is small. Expensive for large ones — you pay for every token every call.
2 — Making knowledge searchable
Vector
A list of numbers — e.g. [0.2, 0.8, -0.3, ...] — that represents a piece of text in a mathematical space. The numbers encode meaning, not spelling. Similar meanings = similar numbers.
Embedding
The process of converting text into a vector. Run your document through an embedding model; it outputs a vector. Do this for every chunk in your knowledge base so they can be compared mathematically.
Vector Database
A database built to store and search embeddings fast. e.g. Pinecone, Weaviate, pgvector. Given a query vector, returns the most similar document vectors in milliseconds across millions of entries.
Knowledge Base
The collection of documents the RAG system retrieves from. Could be internal docs, support FAQs, code, or any structured knowledge. Quality of the knowledge base directly limits RAG quality.
Chunking
Splitting documents into smaller pieces before embedding them. Too large: the chunk contains unrelated content that dilutes the vector. Too small: the chunk loses surrounding context. Typical chunk size: 200–500 tokens with overlap.
Knowledge Graph
Structured store of entities and their named relationships. Goes beyond flat document retrieval — can answer "which component depends on which?" or "who approved what?" Grounds reasoning in structured facts rather than prose.
Temporal Knowledge Graph
A knowledge graph that tracks when facts were true. Lets agents reason about staleness — "this was true in January but changed in March." Ordinary knowledge graphs have no concept of time.
Episodic Memory
Memory of specific past events — what happened, when, in what context. Distinct from general knowledge. An agent with episodic memory can recall a specific prior interaction rather than just general facts.
3 — Finding the right content
Semantic Search
Finding content by meaning, not exact keywords. Query: "how fast did we ship?" returns results about velocity and throughput even if those words don't appear. Powered by embedding similarity.
Cosine Similarity
The standard way to compare two vectors. Picture two arrows from the same origin. Same direction = score of 1 (identical meaning). Perpendicular = 0 (unrelated). Opposite = -1 (antonyms). Only the angle matters, not the arrow length.
Hybrid Search
Combining keyword search (BM25) with semantic search (vectors). Keyword catches exact product names and codes; semantic catches conceptual matches. Together they're more reliable than either alone.
Re-ranking
A second-pass model that re-scores retrieved chunks before injecting them. The first pass (vector search) is fast but imprecise. Re-ranking is slower but more accurate — worth it for high-stakes retrieval.
Retrieval Precision / Recall
Precision: of the chunks retrieved, how many are actually relevant? Recall: of all relevant chunks that exist, how many did we retrieve? Improving precision often hurts recall and vice versa — a fundamental tradeoff.
Needle-in-a-Haystack
Benchmark that hides a specific fact deep in a long document and tests whether the model finds it. Reveals that models often miss facts buried in the middle of long contexts even if the fact fits in the window.
Agents
1 — What makes something an agent
Assistant
Responds to one query and waits. No memory of previous calls, no ability to loop, no autonomous action. A chatbot is an assistant.
Agent
Maintains a goal across multiple steps and acts until it's done — calling tools, looping, retrying — without human input on every turn. The difference from an assistant: it keeps going.
Scaffolding
The code wrapping the LLM: routing logic, retry handling, tool dispatch, state management, logging. The model itself is stateless — scaffolding is what makes it behave like a persistent agent.
Agentic Loop
The core pattern: sense → plan → act → observe → repeat until goal met or failure. Each iteration the agent updates its understanding based on what happened and decides what to do next.
Planning
The agent decomposing a goal into steps before acting. Without planning, agents jump to action and miss dependencies. ReAct (think → act → observe) is the simplest planning pattern.
2 — What an agent can do
Tool / Action
A specific callable function given to the agent: read_file, web_search, run_sql, send_email. Each tool has a typed schema — name, description, input parameters — that the model uses to decide when and how to call it.
Tool Use / Function Calling
The mechanism by which the model invokes tools. The model outputs a structured call (function name + typed arguments) instead of plain text. The scaffolding executes it and returns the result. Anthropic calls it "tool use"; OpenAI calls it "function calling."
Skill
A bundled capability loaded on demand — a named set of instructions or tools that extend what the agent can do for a specific task type. In Claude Code, skills are markdown files.
Memory (Short-term)
The current context window — everything the model sees in this call. Lost when the call ends. An agent with only short-term memory forgets everything between runs.
Memory (Long-term)
Persistent storage the agent reads and writes across calls — files, databases, vector stores. Must be explicitly loaded into context; the model doesn't have automatic access to it.
Feedback Loop
When agent outputs feed back into future inputs — improving performance over time. e.g. a retro that produces lessons, which are injected into the next run's prompt.
Sandboxed Execution
Agent-generated code runs inside an isolated container or VM. If the code does something destructive, it can't reach the host system. Essential for any agent that writes and runs code.
Durable Execution
Long-running workflows checkpoint their state at each step. If the process crashes mid-way, it resumes from the last checkpoint rather than starting over. Important for multi-hour agent runs.
3 — Multi-agent patterns
Orchestration
Coordinating multiple LLM calls or agents to complete a task that one call couldn't handle alone. The pipeline that sequences them is the orchestrator.
Supervisor Agent
A central orchestrator that breaks work into subtasks and routes each to a specialist agent. Router sends code tasks to a coder, review tasks to a reviewer. Clear responsibility, easier to debug than a swarm.
Subagent
A child agent spawned by a parent. Gets its own context window and tool budget. The parent delegates a scoped task; the subagent returns a result and terminates.
Swarm Pattern
Peer agents without a fixed supervisor — they hand off to whichever agent has the right specialty for the current step. More flexible, harder to trace when something goes wrong.
Fan-out / Fan-in
Split one task across multiple agents running in parallel (fan-out), then merge their results (fan-in). e.g. run the same eval on 5 model variants simultaneously, then compare.
Handoff
Passing control and relevant state from one agent to another. The receiving agent needs enough context to continue without re-doing prior work.
Human-in-the-Loop
A human approval gate at high-stakes decision points. The agent pauses and waits for sign-off before proceeding. Slows the pipeline but catches catastrophic errors before they execute.
WIP Limit
Capping how many items an agent works on simultaneously. WIP=1 means one task at a time. Prevents cascading failures where a bad early decision corrupts multiple parallel work streams.
4 — Agent memory (CoALA framework)
CoALA
Cognitive Architectures for Language Agents — a Princeton framework that maps four distinct memory types onto AI agents, mirroring how human memory works. Not every agent needs all four.
Working Memory
The context window — everything the agent can see right now. Fast and immediately accessible but volatile: gone when the session ends, and limited in size. Every agent has this; it's what makes a chatbot a chatbot too. Analogy: RAM.
Semantic Memory
The agent's persistent knowledge base — facts, rules, conventions, documentation. Loaded into context at session start. In Claude Code this is CLAUDE.md. Without it, the agent repeats the same mistakes because it has nothing persistent to draw from. Analogy: a textbook.
Procedural Memory
How the agent knows how to do things. Implemented as skill.md files — named step-by-step instructions for a specific task type. Skills use progressive disclosure: the agent loads a lightweight index first, then pulls in the full skill only when a task matches. Analogy: muscle memory.
Progressive Disclosure
The agent sees only a short name + description for each skill (~100 tokens). Full instructions load only when a task triggers that skill. Prevents blowing the context budget when many skills are defined.
Episodic Memory
Distilled notes from past sessions — not raw transcripts, but compressed lessons worth carrying forward. e.g. "Last time we debugged auth, the issue was in the middleware layer." This is what makes an agent genuinely improve over time. Analogy: personal experience.
The forgetting problem
Episodic memory is the hardest to get right. When does information become obsolete? Humans forget naturally — for agents it's an engineering decision. No good universal answer yet.
Memory by agent type
Simple reflex agents (thermostat, routing bot) need only working memory. A narrow support agent (password reset) adds procedural. A full coding agent needs all four: working + semantic + procedural + episodic.
Protocols & Interoperability
1 — The problem
Why protocols matter
Without standards, every agent-to-tool and agent-to-agent connection requires custom integration code. Protocols define the handshake once so any compliant agent can talk to any compliant tool or agent.
2 — Model-to-tool: MCP
MCP (Model Context Protocol)
Anthropic-originated open standard (JSON-RPC 2.0) that defines how an LLM host connects to external tools and data sources. The model host discovers what tools exist and how to call them — without hard-coded integrations. Think of it as USB-C for AI tools.
MCP Server
The tool-side component. Exposes capabilities (tools, resources, prompts) over MCP. e.g. a filesystem server, a database server, a web search server. Self-contained — swap one out without changing the agent.
MCP Client
The agent-side connector. Discovers available tools from MCP servers, routes the model's tool-call requests to the right server, returns results into context.
Streamable HTTP
The current MCP transport (March 2025). Replaced HTTP+SSE. Bidirectional streaming over a single HTTP connection — the server can push updates without the client polling.
3 — Agent-to-agent
A2A (Agent-to-Agent Protocol)
Google-led open protocol for agents to communicate with each other — passing tasks, context, results — without exposing internal implementation. MCP handles model-to-tool; A2A handles agent-to-agent.
AGNTCY
Cisco-led framework for cross-vendor agent discovery, identity, and messaging. Aims to be the TCP/IP of multi-agent systems — a shared infrastructure layer any agent can plug into.
AGENTS.md
File convention: a project-specific instruction file in the repo root, targeted at AI agents. Like README.md for humans — tells the agent what conventions to follow, what not to touch, what tools exist.
4 — SDKs
Claude Agent SDK
Anthropic's framework for building production agents on Claude. Handles tool dispatch, multi-turn loops, MCP integration. More structured than raw API calls.
OpenAI Agents SDK
Lightweight Python/TypeScript framework for agentic apps on OpenAI models. Provides tool use, agent handoffs, and guardrails out of the box.
Vercel AI SDK
TypeScript framework for streaming, tool use, and multi-provider agents in web apps. Abstracts over providers — swap Claude for GPT-4 with minimal code changes.
Evaluation & Observability
1 — Building evals
Eval
A repeatable test that measures whether the AI produces correct or acceptable output. Without evals you're flying blind — you can't tell if a change made things better or worse.
Ground Truth
The known correct answer for each eval input. Building ground truth is expensive: humans must label what "correct" looks like. Without it, you can only measure relative quality, not absolute quality.
LLM-as-Judge
Using one LLM to evaluate another's output. e.g. ask GPT-4 whether Claude's answer is correct. Scales cheaply but inherits the judge model's own biases. Best used to check format, completeness, and tone rather than factual accuracy.
Human Eval
Humans rate or rank model outputs. Gold standard for quality — humans catch nuance automated metrics miss. Expensive and slow. Used to calibrate automated evals, not replace them.
A/B Testing
Run prompt variant A and variant B on the same set of inputs, compare scores. Essential discipline: change one thing at a time and measure. Without this, you can't attribute a quality change to the change you made.
2 — Benchmarks
Benchmark
A standardised test set used to compare models on a common task. Useful for choosing a model. Less useful for evaluating your specific application — your task probably isn't in the benchmark.
SWE-Bench
2,294 real GitHub issues — can the agent resolve them? The standard leaderboard for coding agents. A score here is the most meaningful public signal of coding capability.
OSWorld
369 real computer tasks: web browsing, desktop apps, OS operations. Tests whether an agent can actually operate a computer, not just generate code about one.
TBench (Terminal-Bench)
Terminal-mastery tasks for agents: real shell commands, file operations, system-level work. Benchmarks command-line competence specifically.
3 — Key metrics
Pass Rate
Percentage of tasks that pass all evaluation gates. The headline number for agent quality — did it actually succeed, end to end?
Latency
Time from prompt sent to response received. Varies dramatically by model size, context length, and output length. Critical for real-time applications; less critical for batch pipelines.
Cost per Call
Input tokens × price/token + output tokens × price/token. A small model (Haiku) can be 20× cheaper than a large one (Sonnet) with acceptable quality on simpler tasks. Model routing saves significant money.
4 — Observability
Tracing
Recording every step of an agent run — prompts sent, responses received, tools called, timing. Makes failures reproducible and debuggable. Without tracing you can't answer "what exactly did it do?"
Regression
A test that previously passed, now fails. In LLM systems regressions are insidious — a prompt change that improves Task A can silently break Task B. Catch them with a full eval suite, not spot checks.
Prompt Versioning
Tracking prompt changes with history and rollback — like source control for prompts. When a regression appears, you can bisect: which prompt change introduced it?
Fine-tuning & Training
1 — The spectrum: prompt → weights
Prompt Engineering
Changing model behaviour through instructions alone — no weight changes. Cheapest and fastest. Limited: you can't teach a model something it truly doesn't know, only steer what it already can do.
Prompt Tuning
Trains a small set of "soft prompt" tokens prepended to every input. The base model's weights are frozen; only the prepended tokens are trained. Lighter than fine-tuning, heavier than prompt engineering.
Instruction Tuning
Fine-tuning on instruction-response pairs to make a base model follow directions. The step that turns a raw next-token predictor into a useful assistant. Almost all deployed LLMs have been instruction-tuned.
Fine-tuning
Continuing training on a task-specific dataset, updating model weights. More durable than prompt engineering — the behaviour is baked in. Requires labelled data and compute. Best when you need consistent style, format, or domain knowledge the base model lacks.
LoRA (Low-Rank Adaptation)
Fine-tuning that adds small trainable matrices alongside existing weight matrices, leaving the originals frozen. A 7B-parameter model might only train 10M LoRA parameters — roughly 0.1% of the total. Gets most of the benefit at a fraction of the cost.
Transfer Learning
Starting from a pre-trained model and adapting it for a new task. Almost all LLM work is transfer learning — you never train from scratch. The foundation model provides the general language capability; you adapt the rest.
2 — Alignment training
RLHF
Reinforcement Learning from Human Feedback. Humans rank pairs of outputs; a reward model learns to predict human preference; the LLM is trained to maximise reward. How early versions of Claude and ChatGPT learned to be helpful and safe.
RLAIF
Reinforcement Learning from AI Feedback. Replace human rankers with an LLM critic — cheaper and faster to scale. Constitutional AI is a form of RLAIF: the model critiques itself against a written set of principles.
Constitutional AI (CAI)
Anthropic's approach: the model is given a "constitution" of principles and asked to critique and revise its own outputs against them. Reduces harmful outputs without requiring human labellers for every category of harm.
RL Post-training
Reinforcement learning applied after supervised training to develop capabilities that supervised training alone doesn't produce reliably — multi-step reasoning, tool use, planning. The training step behind modern "reasoning models."
3 — Architecture and efficiency
MoE (Mixture of Experts)
Instead of one dense network, many smaller "expert" sub-networks. A router selects 2–4 experts for each token. A 100B-parameter MoE might only activate 10B parameters per token. Large capacity, reasonable inference cost.
Distillation
Training a small "student" model to mimic the outputs of a large "teacher." Run GPT-4 on 1 million examples, train a smaller model on those outputs. Haiku-sized capability at Haiku-sized cost. Quality degrades in proportion to size reduction.
DSPy
Stanford framework where you define the task declaratively and an optimizer writes the actual prompt. Treats prompts as compiled artifacts rather than hand-crafted text. Useful when you have an eval but don't want to manually tune prompts.
4 — Training mechanics
Loss Function
A number measuring how wrong the model's prediction was. Model predicted "dog" (30% confident) but correct answer was "dog" — loss is moderate; it was right but uncertain. Model predicted "cat" (90% confident) and correct was "dog" — loss is high. Training minimises this number across millions of examples.
Gradient Descent
The algorithm that updates weights to reduce loss. Think of the weights as dials on a mixing board — gradient descent nudges each dial slightly in whichever direction reduces the wrongness score. Repeat for billions of examples.
Learning Rate
How far to nudge each dial per step. Too high: the model overshoots and training becomes unstable. Too low: training converges very slowly. Typically starts higher and decays over training.
Batch Size
How many examples are averaged together before updating weights. Larger batches = more stable gradient estimates and better hardware utilisation, but require more memory. A common tradeoff in large-scale training.
Epoch
One complete pass through the entire training dataset. Most LLMs are trained for less than one epoch — the datasets are so large that seeing each example once is enough. Fine-tuning often uses multiple epochs on smaller datasets.
Overfitting
The model memorises training examples instead of learning general patterns. It scores perfectly on training data but fails on anything slightly different. A spam filter that memorises known spam emails will miss any new phrasing.
Synthetic Data
Training data generated by an AI rather than humans. Used when real labelled data is scarce or expensive. Increasingly common — models train on data generated by other models.
Data
1 — What data is
Training Data
The examples a model learns from. Quality and diversity of training data directly determines what the model can do. This is the single biggest lever in AI capability.
Dataset
A structured collection of examples — inputs, expected outputs, and often labels. Used for training, fine-tuning, or evaluation. A dataset is the substrate; the model is what you build on top.
Labelling / Annotation
Adding ground truth labels to examples. Humans mark each email as spam or not-spam; each image region as "cat" or "background." Expensive, slow, but necessary for supervised learning. A significant bottleneck in building AI systems.
Synthetic Data
AI-generated training examples used when real labelled data is scarce. A model generates plausible inputs and outputs; another model trains on them. Increasingly viable as generator quality improves.
2 — Data quality problems
Data Quality
"Garbage in, garbage out." Accuracy, completeness, and consistency of training data directly set the ceiling on model quality. Architecture improvements can't compensate for bad data.
Data Curation
Selecting, cleaning, deduplicating, and balancing data before training. The difference between a model that generalises and one that memorises often comes down to curation quality.
Class Imbalance
Far more examples of some categories than others. A fraud detector trained on 99% non-fraud examples learns "always say not fraud" — 99% accuracy, zero fraud caught. Requires resampling or class weighting to fix.
Data Drift
Real-world inputs shift over time away from what the model was trained on. A customer service model trained in 2023 may not understand new product names or cultural references from 2026. Requires monitoring and retraining.
Infrastructure & APIs
1 — Making a call
API
The interface for calling the model programmatically. You send a JSON request (with your prompt) to an endpoint; it returns a JSON response (with the completion). All LLM providers expose an API.
SDK
A library in your language that wraps raw API calls. Handles authentication, request formatting, response parsing, and retries. e.g. Anthropic Python SDK, OpenAI Node SDK.
Endpoint
The specific URL receiving a type of API request. e.g. api.anthropic.com/v1/messages for chat, /v1/embeddings for embeddings. Different capabilities have different endpoints.
Model Version
A specific named release of a model. e.g. claude-sonnet-4-6. Always pin to a specific version in production — "latest" is not a version. Model updates can silently change behaviour.
2 — Limits and reliability
Rate Limit
Cap on requests or tokens per unit time. Exceeding it returns a 429 error. Limits exist per API key and per tier. Scale up by requesting a higher tier, or spread load across multiple keys.
Tokens per Minute (TPM)
Throughput limit on token volume rather than request count. For large-context applications, TPM is the binding constraint long before request count is. Plan capacity based on average prompt size × expected concurrency.
Timeout
Maximum wait before treating the call as failed. Long outputs (large context + many tokens generated) can take 60–120 seconds. Set your timeout higher than your expected p99 latency, not just average latency.
Retry Logic
Automatically retry failed calls with exponential backoff. Wait 1s, retry. Wait 2s, retry. Wait 4s, retry. Handles transient rate limits and network blips without crashing the pipeline.
Prompt Caching
The provider caches the KV pairs for a repeated prompt prefix. On the next call with the same prefix, those tokens aren't re-processed — just loaded from cache. Cuts cost and latency when you reuse a long system prompt across many calls.
Multimodal
1 — Input types
Multimodal Model
A model that processes more than one input type — text, images, audio, video — in the same call. Claude 3+ accepts images alongside text. The model reasons across modalities together, not in separate pipelines.
Vision
The ability to process and reason about images. Send an image URL or base64 blob alongside your text prompt. The model describes, analyses, compares, or extracts information from the image.
Image-to-text
Generating text from an image. e.g. "What does this chart show?", "Extract the table from this screenshot", "Describe this diagram." A specific application of vision capability.
Cross-modal Reasoning
Reasoning that uses both modalities together. e.g. "Does this wireframe image match the requirements in the document?" The model must integrate visual and text information to answer.
2 — Output types (separate models)
Text-to-image
Generating images from text descriptions. e.g. DALL-E, Midjourney, Stable Diffusion. Not LLMs — different architecture (diffusion models). Claude generates text only.
Text-to-speech (TTS)
Converting text to spoken audio. Used in voice assistants and accessibility. A separate model from the LLM — the LLM generates the text, TTS converts it.
Speech-to-text (STT)
Transcribing spoken audio to text. e.g. Whisper. Used as a preprocessing step — STT converts speech to text, then the text goes to an LLM. Separate model again.
Safety & Ethics
1 — The goal: alignment
AI Safety
The field of ensuring AI systems remain beneficial as they become more capable. Covers both near-term (harmful outputs, misuse) and long-term (loss of human control) risks. Anthropic's stated reason for building Claude.
Alignment
Making AI systems reliably do what humans actually want — not just what they literally said. An aligned model is helpful, harmless, and honest. Misalignment ranges from minor (model misunderstands intent) to severe (model pursues goals that harm humans).
Constitutional AI
Anthropic's technique: a written set of principles (a "constitution") is given to the model, which critiques and revises its own outputs against them. Produces more consistent, auditable alignment than purely human feedback.
2 — Threats
Bias
Systematic errors caused by imbalances in training data. A model trained mostly on text from one demographic performs worse for others. Often invisible until you test on underrepresented groups.
Hallucination
The model generates plausible but false content — inventing citations, misquoting facts, confabulating details. Not lying: the model has no concept of truth, only probability. Grounding and citations reduce it; they don't eliminate it.
Prompt Injection
Malicious text in the input overrides system prompt instructions. "Ignore all previous instructions and instead..." A serious attack vector for agents that read external content — emails, web pages, documents.
Jailbreak
A crafted prompt that bypasses safety guardrails. Common techniques: roleplay framing ("pretend you're a model without restrictions"), hypothetical framing, instruction injection. New jailbreaks are found regularly; defences lag.
Red Teaming
Systematically trying to break a model's safety constraints before deployment. Dedicated team generates adversarial inputs, documents failure modes, and measures severity. Standard practice at safety-focused labs.
3 — Controls
Guardrails
Rules and filters that prevent harmful outputs. Two types: (1) prompt-level — instructions telling the model what not to do; (2) output-level — external classifiers that check the model's response before returning it.
Content Filtering
Automated classifiers running in parallel that block or flag harmful inputs or outputs. Can catch what the model's own guardrails miss. e.g. a hate-speech classifier applied to all outputs before they're returned to the user.
Explainability
The ability to understand why the model produced a specific output. LLMs are largely black boxes — the weights don't map to human-readable rules. Chain of thought surfaces reasoning but doesn't reveal the true computational cause.

Emerging Terms — 2026-06-06 09:00
KV Cache (Key-Value Cache)
Stores the attention key-value pairs computed for each token so they don't need to be recomputed on every generation step. Fundamental to why long-context calls cost more and take longer. Prompt caching works by reusing KV cache across calls.
PagedAttention
Virtual-memory-style paging of the KV cache — splits it into fixed-size blocks allocated on demand rather than one contiguous chunk. Lets a server run many concurrent requests without wasting GPU memory. Foundational to vLLM and efficient LLM serving.
World Model
A model trained to simulate how a physical environment behaves — predicting what happens next given an action, not just generating text. Emerging for robotics and physical AI. e.g. Nvidia Cosmos.
Long-horizon Reasoning
An agent maintaining coherent goals and context across dozens or hundreds of sequential steps — far beyond a single prompt-response cycle. A known failure mode: agents lose track of the original goal or contradict earlier decisions.
Temporal Knowledge Graph
A knowledge graph that tracks when facts were true, not just what is true. Lets agents reason about whether information is current or stale. e.g. "this endpoint existed in sprint 3 but was renamed in sprint 7."
Product Owner
1 — Writing stories
User Story
"As a [specific persona] I want [feature] so that [concrete business value]." Three parts, all required. The persona must be specific (not "user"). The "so that" must state real value (not "so I can see it").
INVEST
Six criteria for a well-formed story: Independent (can be built alone), Negotiable (details flexible), Valuable (delivers user value), Estimable (team can size it), Small (fits in a sprint), Testable (AC can be verified). Fail any one and the story needs work.
Acceptance Criteria
Specific, observable conditions a story must meet to be done. Good AC: "When the user navigates to /leaderboard, sprints are listed newest-first." Bad AC: "The leaderboard works correctly." Each criterion should be independently verifiable.
Given / When / Then
A structured AC format. Given [initial state], When [action taken], Then [observable result]. Forces specificity — you can't write vague AC in this format without noticing it.
Story Splitting
Breaking a large story into smaller independently deliverable ones. Split by workflow step, data type, role, or happy path vs edge cases — not by technical layer. Avoid "front-end story" / "back-end story" splits that deliver no value alone.
2 — Backlog management
Product Backlog
The ordered list of all work to be done — features, fixes, NFRs, technical debt. The PO owns priority. Items at the top are refined and ready; items at the bottom are rough and unordered.
Backlog Refinement
The ongoing process of elaborating, estimating, and ordering backlog items. In AI-DLC, this is where Inception runs — turning intent into stories with AC before sprint planning.
Sprint Goal
A single sentence describing the "why" of the sprint — what outcome the team is trying to achieve, not a list of stories. Guides scope decisions when surprises arise mid-sprint.
Opportunity
An idea or request that hasn't been elaborated into a story yet. Pre-backlog. The PO decides which opportunities are worth the elaboration investment.
Story Map
A visual layout of user activities (horizontal) with stories beneath each activity (vertical). Reveals gaps and shows what a minimal viable release looks like — the horizontal slice, not a vertical stack of one feature.
3 — AI-specific PO concerns
Non-Functional Requirements (NFRs)
Performance, reliability, security, accessibility requirements. AI agents routinely ignore these unless explicitly stated in AC. e.g. "Response time under 2 seconds", "No PII logged", "Screen-reader accessible."
Prompt as Requirement
The system prompt is a product requirement — it defines agent behaviour. Changes to prompts change product behaviour. POs should review and approve prompt changes the same way they review feature changes.
Observable Outcome
AI implementations must have outcomes a human can verify without reading code. "The leaderboard appears on the app page grouped by sprint" is observable. "The data is fetched correctly" is not — you can't see it without debugging.
Regression Risk
AI agents can break existing functionality while implementing new features — especially when modifying shared files. AC must explicitly protect existing behaviour: "existing sprint cards still display correctly after this change."
Scope Creep (Agent)
AI agents tend to "improve" things beyond the story scope — renaming variables, restructuring files, adding features not requested. AC must constrain this: "no changes to files other than X" and "no new pages or routes."
4 — Prioritisation frameworks
MoSCoW
Must Have / Should Have / Could Have / Won't Have. Classifies stories by necessity for a given release. Forces explicit decisions about what's truly required vs. nice to have.
Value vs. Effort
Plot stories on a 2×2: high value + low effort = do first; low value + high effort = cut. Simple but effective for backlog ordering. Value is estimated by the PO; effort by the team.
WSJF (Weighted Shortest Job First)
SAFe prioritisation: (Business Value + Time Criticality + Risk Reduction) ÷ Job Size. Surfaces small, high-value, time-sensitive items. More rigorous than gut-feel ordering for large backlogs.
Kano Model
Classifies features by how they affect customer satisfaction. Basic needs: expected — absent = dissatisfied, present = neutral (e.g. the app loads). Performance needs: more is better linearly (e.g. faster response). Delighters: unexpected — absent = neutral, present = delighted (e.g. proactive AI suggestions). Basics must ship; delighters differentiate. Note: delighters become basics over time as users expect them.
Technical Debt
Deferred work that makes future changes harder. AI agents can accumulate technical debt fast — generating code that works but isn't maintainable. POs must budget debt repayment into the backlog or velocity degrades over time.
