Full Workflow

From Messenger idea to deployed feature
1 Capture — Messenger

You type a message in Messenger. Haiku classifies it instantly into one of three types:

Req Requirement — Haiku generates 3 story title options varying in scope or approach. You click one and it lands in the Opportunity Backlog with opportunity: true.
Inq Inquiry — Haiku extracts keywords, searches backlog.json with stop-word filtering, and returns rich status for matching items: done, failed, in sprint, or pending.
Other Other — Haiku replies conversationally. Nothing is added to the backlog.
2 Elaborate — Backlog Board

You drag an item from Opportunity Backlog → Story Backlog. On drop, Haiku auto-generates a full user story (As a user, I want...) with 3–4 short, testable acceptance criteria.

The card pulses with a "generating story..." animation while in flight. When done, a ▸ chevron appears — clicking the card body expands to show the AC. Expansion state persists across re-renders.

3 Sprint Planning — Backlog Board

You drag stories from Story Backlog → Sprint Backlog. Set an optional Sprint Goal in the field at the top of the sprint column. Order determines execution sequence — reorder to reprioritize.

When ready, click Start Sprint. The server spawns agent.py --sprint as a background subprocess and the pipeline takes over.

4 Per-Story Pipeline — fully automated
a Wisdom + context injection. Before calling Sonnet, the prompt is built with two stacked sections: RULES (synthesized cross-sprint bullet directives from wisdom.json) and THIS SPRINT (intra-sprint retro findings from the item just before this one). Both are token-compressed.
b Sonnet implements. Receives CSS-stripped index.html and the last 1 changelog entry. Writes a user story with AC, patches the file, bumps the patch version, adds a changelog entry.
c Automated tests (DoD). Four checks run: index.html exists, title present, version numbers match between files, changelog entry exists for new version. Fail → rollback, item marked failed.
d Haiku code review. Hermes reviews the diff for technical quality only — bugs, broken HTML/CSS, scope creep. Business requirements not evaluated here. Reject → rollback.
e Haiku AC check. Hermes checks whether the implementation satisfies the original idea and each acceptance criterion. Code quality assumed correct — purely requirements validation. Reject → rollback.
f Deploy. Git commit + push to GitHub. GitHub Pages goes live in ~30 seconds. Full audit trail (story, diff, test results, Hermes verdicts, timestamps, tokens) saved to backlog.json in the same commit.
5 Per-Story Retro — runs after every item
Wisdom Haiku analyzes all items processed so far this sprint. Writes findings to retrospective.json categorized as: fail (recurring failure patterns), ok (what worked), do (improvements), note (observations).
Wisdom synthesize_wisdom() re-reads all findings from all sprints ever, asks Haiku to distill them into 6–8 terse directive bullets (≤12 words each), and overwrites wisdom.json. The next story gets the freshly updated RULES block.
Context retro_context is reloaded from retrospective.json so the next story's THIS SPRINT block reflects what just happened — including whether the previous item passed or failed and why.
6 Repeat Until Sprint Empty

Steps 4–5 repeat for each story in the sprint queue. By story 3, the agent has seen what failed in stories 1 and 2 of this sprint (THIS SPRINT) plus the freshly updated all-time wisdom (RULES). The feedback loops compound within the sprint.

When the queue is empty, the sprint ends. The Retro page shows all findings. The System Retro column shows the current synthesized wisdom ready for the next sprint.
